# C：检索、模型与评测（待本人复核的模块稿）

本模块负责把已经解析、具有稳定文件身份和页码的文本块转成可搜索结果。实现从真实仓库现状出发：初始仓库只有 case/job 的示范业务，没有文件版本、文本块或搜索接口。因此本分支提供可独立验证的检索数据合同、关键词搜索、本地多语言 embedding、向量处理函数和评测工具；公共迁移整合、扫描授权、PDF 解析和界面仍分别由 A、B、D 完成。当前的合成文本导入工具用于并行开发，不作为真实 PDF 处理证据。

关键词通道使用 PostgreSQL 的全文查询和 GIN 索引。英文采用完整单词，中文先做 NFKC 规范化，再把连续中文串拆为双字词，词不会跨标点或空格拼接。这一方案不要求额外的中文数据库分词插件，便于在 Docker 和备用电脑复现。检索分数包含查询词覆盖率、完整短语命中和文件名命中，分数是排序信号，不代表结果正确的概率。SQLite 开发适配器采用同一套切词和打分合同，正式 PostgreSQL 则实际执行全文匹配。

语义通道采用固定 revision 的 `intfloat/multilingual-e5-small`，输出 384 维 L2 归一化向量。查询与段落分别加入 E5 的 query 和 passage 前缀，并用 attention mask 对隐藏状态做平均池化。模型文件通过显式准备命令下载，逐文件计算 SHA-256；运行时只读取校验后的本地文件，不自动下载，不向云端模型发送文本。该模型在本机 CPU 上完成了真实推理，模型缓存需另外交给备用电脑，Git 只保存代码和模型清单合同。

向量处理函数 `embed_version` 由异步调度器或独立 CLI 调用，每批最多处理十六段文本。它先收集并验证所有批次的向量，再在调用者的事务中发布结果；若第二批出现超时，先前取得的向量也不会形成半成品写入。基本文本、页码和已有向量保留，调用者获得明确错误码后记录重试。函数不自行提交事务，便于 A 统一管理任务状态、尝试次数和数据库提交。

公开的 `POST /search` 支持关键词、语义和混合三种模式。混合模式默认以 0.65 的关键词权重和 0.35 的语义权重计算排序。每个通道先按文件选块，避免长文档用大量分块占满候选池；两个通道合并后再次按文件去重。结果返回文件 ID、版本 ID、块 ID、起止页码、原文节选、匹配理由和各通道分数。只有当前、就绪并且文件哈希与版本哈希一致的数据可以参与搜索，旧版本内容不会继续展示为当前证据。磁盘授权和原文件核验需要与 A/B 正式接口整合。

为了保证关键词主路径可用，模型关闭、AI 服务停止、HTTP 超时、模型版本不符或向量尚未就绪时，响应会明确标注 `degraded=true`，将 `effective_mode` 改为 keyword，并保留请求的原始 mode。部分文档尚未向量化时也会提示部分降级。单元测试覆盖了这些失败路径，另用真实 API/AI 子进程验证：停止 AI 进程后，五条关键词基准仍全部返回正确文件和页码，没有云端回退。

内部评测使用十二份手写合成文档、十五个带页码文本块和十条冻结查询，其中五条关键词、五条语义。答案在首次模型评测前固定，评测记录保留语料与答案哈希以及逐条返回结果。关键词按 Top-1 的文件与页码同时正确计分，结果为 5/5；语义按 Top-3 中存在正确文件且正确页码计分，结果为 4/5。失败的账户查询命中了正确文件却选择第 3 页，而答案是第 1 页，所以仍计为失败，没有改写答案。该十条查询是内部烟雾测试，不能代表泛化性能或真实 PDF 证据链已经通过。

交接时需要 A 整合公共模型、有效 root 范围和向量任务分发，B 确认真实原文、版本和页码，D 接入返回字段及降级提示。当前未实现独立 cross-encoder 重排，不声称具备该能力。下一步应在团队冻结的真实 PDF 上复验关键词、证据一致性、语义失败样例和整机离线演示。代码与材料通过 C 独立分支供团队审阅，团队封板和向 main 合并另行执行。
