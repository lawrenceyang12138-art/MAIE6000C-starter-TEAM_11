# B - Bounded relation read and append-only review (10.19 PM)

Owner: B (read files / PDF parsing and evidence quality)
Module: `services/parsing/graph.py`

## The two properties this step delivers

**Bounded reads.** The schedule asks for a bounded relation read, not a graph
walk. The limit is enforced in code, so a document that produced fifty
candidates cannot quietly become a fifty-node graph. Asking for a thousand
still returns at most the cap.

**Append-only review behind a revision guard.** A decision never overwrites a
previous one; it is appended with the next revision number. The caller passes
the revision it last saw, and the write is refused if that is no longer
current. Two people reviewing the same relation at the same moment therefore
produce a visible conflict instead of one silently discarding the other's
decision.

This is the behaviour the schedule calls for in the Activity D discussion:
human review uses an expected revision to prevent duplicate or concurrent
overwrites.

## End-to-end run against real PostgreSQL

```
docker compose run --rm --no-deps -v "$PWD/scripts:/app/scripts" api \
  python scripts/demo_relation_review.py tests/fixtures/relations/entities.pdf
```

Observed output:

| Step | Result |
| --- | --- |
| Document ingested | 2 pages, 2 chunks |
| Relations stored | 3 |
| Candidates shown | person `Chen` (page 1), project `File Management Assistant` (page 1), topic `Schema Design` (page 1) |
| Reviewer A confirms | revision **1** |
| Reviewer B with a stale view | **refused**, `review_conflict` |
| Reviewer B re-reads and rejects | revision **2** |
| Effective decision | `rejected` at revision 2 |

Each candidate was displayed with the quote that justifies it, so a reviewer
sees why the system proposed it rather than being asked to trust a label.

## Why the guard matters more than it looks

Without it, the second reviewer's rejection would have replaced the first
reviewer's confirmation with no trace, and the history of who decided what
would be gone. With it, the earlier decision is preserved as revision 1 and the
later one is appended as revision 2. The effective answer is the latest
revision, and everything before it is still readable.

Human decisions are the one thing in this system that is never regenerated by
reprocessing, which is why relationships are found-or-created rather than
replaced: a review points at a relation, and replacing the row would discard
the review with it.

## Verification

Command:

```
docker compose run --rm --no-deps api pytest -q tests/unit/test_parsing_graph.py
```

Result: **7 passed**.

- relations come back with their quote, page, origin and producer revision
- an unreviewed relation reports decision `None` at revision 0
- the read is bounded: asking for more than the cap does not exceed it, and a
  limit of zero returns nothing
- the first review becomes revision 1
- a stale expected revision is refused with `review_conflict`, and the earlier
  decision remains effective
- reviews are append-only: both decisions are retained, in revision order
- an invalid decision value is refused and nothing is written
- reviewing an unknown relation is refused
- a correction stores the entity it points at, and that pointer is served back
  with the relation
- a correction that names no replacement is refused
- a confirmation that tries to carry a replacement is refused
- a correction pointing at an entity that does not exist is refused

Full suite: **80 passed, 2 skipped**. `ruff check .` clean.

## What is still missing

- **No HTTP endpoints.** Both the read and the review exist as handlers; the
  routes belong to A.
- **A correction cannot create an entity.** `corrected_entity_id` must point at
  a row that already exists, so correcting towards something the extractor
  never produced is a two-step job: create the entity, then point at it.
- **Nothing calls any of this from the worker.** The whole chain so far is
  driven by tests and scripts.
